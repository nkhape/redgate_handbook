# Redgate Handbook — Project Context

## What this is
An internal product reference site for Redgate's sales and solutions teams. Built by Nick Hape (Solutions Engineer at Redgate Software). The goal is one fast, easy place for non-technical colleagues to find key info about each product. Available in English and German.

## Stack
Plain static HTML + Tailwind CSS, generated by a small Ruby script. No Rails, no server, no gems beyond the Ruby standard library (`erb`, `yaml`, `json`, `net/http`, `rexml`).

- Content lives in `data/products.en.yml` / `data/products.de.yml` and `data/releases_data.json` (each product/locale keyed separately), plus `data/ui_strings.yml` for interface text (labels, headings, buttons).
- Templates live in `templates/*.html.erb` (layout, home, product — one shared template for every product page, in either language).
- `generate.rb` renders the templates + data into `public/` for both locales — this is the actual served site and is committed to git.
- `fetch_releases.rb` pulls the release-notes RSS feed and asks Claude for both an English and German summary in one call, writing both into `data/releases_data.json`.

## Internationalization (EN/DE)
- English is unprefixed (`/`, `/products/monitor/`); German lives under `/de/` (`/de/`, `/de/products/monitor/`).
- The nav bar has a 🇬🇧/🇩🇪 language switcher that links to the equivalent page in the other language (not just the home page).
- Product names (Monitor, Flyway, Toolbelt Essentials) are treated as brand names and aren't translated; everything else is.
- To add a UI string: add it to both `en:` and `de:` blocks in `data/ui_strings.yml`, then reference it in a template with `t(:key)` (supports `%{placeholder}` interpolation, e.g. `t(:last_updated, date: "...")`).
- To edit product content: edit both `data/products.en.yml` and `data/products.de.yml` — they must have the same keys/structure, just translated values (URLs, icon_urls, and image paths stay identical across locales).

## GitHub Pages base path
GitHub Pages serves this repo (not a `<user>.github.io` repo) at `https://nkhape.github.io/redgate_handbook/`, not at the domain root. `generate.rb` has a `BASE_PATH = "/redgate_handbook"` constant that gets prefixed onto every internal link, image src, and stylesheet href via the `asset()` / `page_path()` helpers. If this ever moves to a custom domain or a `<user>.github.io` repo, change `BASE_PATH` to `""` and regenerate.

## Running locally
```
ruby generate.rb              # regenerate public/ (both locales) from templates + data
ruby -run -e httpd public -p 3000   # serve it (needs `gem install webrick` once — Ruby 4.0 dropped it as a default gem)
```
Note: `generate.rb` bakes in `/redgate_handbook` as a URL prefix (see above), so a plain local server at `http://localhost:3000/` will 404 on `/` — go to `http://localhost:3000/redgate_handbook/` instead, or temporarily set `BASE_PATH = ""` for local-only testing.

To refresh release notes locally you need `ANTHROPIC_API_KEY` set:
```
ANTHROPIC_API_KEY=... ruby fetch_releases.rb        # all products, both languages
ANTHROPIC_API_KEY=... ruby fetch_releases.rb monitor # one product, both languages
```

## Deployment
- Hosted on **GitHub Pages**: https://nkhape.github.io/redgate_handbook/
- The repo is public (required for free-tier GitHub Pages on a repo, not a personal account plan) — checked git history for secrets before making it public; there were none (`config/master.key` was never committed).
- `.github/workflows/deploy-pages.yml` deploys `public/` to Pages via `actions/upload-pages-artifact` + `actions/deploy-pages` whenever `public/**` changes on `main`.
- `.github/workflows/update-content.yml` runs weekly (Mondays), calls `fetch_releases.rb` + `generate.rb`, and pushes the regenerated `public/` + `data/releases_data.json` straight to `main` if anything changed — which in turn triggers the Pages deploy above. Needs an `ANTHROPIC_API_KEY` repo secret to work.
- No longer deployed via Render — `render.yaml` was removed.
- Branch strategy: short-lived feature branches, squash-merged into `main` via PR.

## Product page structure (standard across all products)
1. Header — name + tagline
2. What it does — short description
3. Supported Platforms — database logo icons (devicons CDN)
4. Key Features — tabbed cards (title, description, screenshot, points)
5. Demo Servers (Monitor only)
6. Useful Links — docs, demos, etc.
7. What's New — auto-fetched release notes, refreshed weekly, in both languages

## Key files
- `data/products.en.yml` / `data/products.de.yml` — all product content, per locale
- `data/ui_strings.yml` — interface text (labels, buttons, headings), per locale
- `data/releases_data.json` — cached release notes, nested `{product: {en: {...}, de: {...}}}`, weekly-refreshed, committed to git
- `templates/product.html.erb` — shared product page template
- `templates/home.html.erb` — home page with product cards
- `templates/layout.html.erb` — navbar + language switcher + page shell
- `generate.rb` — renders templates + data into `public/` for both locales; owns `BASE_PATH`
- `fetch_releases.rb` — fetches + bilingually summarises release notes into `data/releases_data.json`
- `assets/` — source images/CSS/icons that `generate.rb` copies into `public/`
- `.github/workflows/deploy-pages.yml` — deploys `public/` to GitHub Pages
- `.github/workflows/update-content.yml` — weekly release-notes refresh + regenerate + commit
